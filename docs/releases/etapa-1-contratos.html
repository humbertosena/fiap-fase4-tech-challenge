Etapa 1 · Validação de dados e contratosv0.1.0-alpha2026-10-11

Garantir que lixo não entre no modelo

Antes de detectar degradação, é preciso confiar no dado que chega. Nesta etapa criamos um dataset de referência sintético, um contrato de dados com 12 regras que bloqueia lotes corrompidos e o modelo baseline que será monitorado nas próximas etapas.

O que foi implementado

Validação de Dados (25 %)

Dataset sintético com DGP explícito

12.000 propostas geradas por um processo gerador documentado (ADR 001): risco latente, renda, bureau, endividamento e tabela Price. Seed 42, arquivo idêntico a cada execução.

Validação de Dados (25 %)

Contrato Pandera

12 regras declaradas uma única vez, com schema estrito (strict=True, coerce=False) e exportação para config/data_contract.yaml (ADR 002).

Validação de Dados (25 %)

Circuit breaker em dois níveis

Violação estrutural bloqueia o lote. Erros de linha vão para a quarentena até 1 %; acima disso o breaker abre. Nunca há imputação silenciosa.

Governança (apoio)

Privacidade por padrão

Relatórios trazem só id_cliente_hash (HMAC-SHA-256 com salt secreto) e o comando scan-pii varre saídas em busca de CPF, e-mail e telefone.

Base para as Etapas 2 e 3

Modelo baseline

HistGradientBoostingClassifier com assinatura MLflow, limiares de F1 e de custo e importância por permutação (ADR 003).

      Política de decisão

      • Estrutural (R01, R02): coluna inesperada, coluna ausente, tipo errado, id nulo ou duplicado → BLOCKED.
      • Linha (R03 a R12): linhas inválidas vão para data/quarantine/<run_id>.parquet se forem até 1 % do lote.
      • Acima de 1 %: problema sistêmico, o breaker abre → BLOCKED.
      • Exit codes: 0 sucesso · 2 lote bloqueado.

      Motivo registrado no relatório do lote corrompido: violação estrutural (R01, R02): lote bloqueado.

      Como os dados nascem (ADR 001)

      1. Um risco latente z ~ N(0, 1) por cliente move score, endividamento, utilização e atrasos.
      2. Renda log-normal com fatores por emprego e região; parcela pela tabela Price limitada a 60 % da renda.
      3. Inadimplência sorteada de um logit explícito, com intercepto calibrado para 6 %.
      4. genero e regiao ficam fora do logit e do modelo.

      5 · Privacidade por padrão

      Pseudonimização

      O identificador nunca aparece em claro fora do dado bruto. Exemplo com o formato do id:

      CLI-XXXXXXXXXX → HMAC-SHA-256 com salt secreto →

      8ab31b6ebc5cf866ae24c9ffbd70451fb806ecf49814db6255077cfc1cdd7470

      Varredura de PII

      O lote corrompido traz uma coluna cpf fictícia (dígito verificador inválido). O contrato a bloqueia como violação estrutural, e credit-sentinel scan-pii reports docs confere que nenhum CPF, e-mail, telefone ou id em claro chegou aos relatórios ou a esta página.

      Como reproduzir

      uv sync --all-groups
      uv run credit-sentinel generate-data --force
      uv run credit-sentinel validate --input data/corrupted/bad_batch.parquet
      uv run credit-sentinel validate --input data/reference/credit_ref.parquet --schema reference
      uv run credit-sentinel train
      uv run credit-sentinel scan-pii reports docs
      uv run credit-sentinel build-explainers --etapa 1
